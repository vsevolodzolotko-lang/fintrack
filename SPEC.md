# FinTrack — спільний фінансовий трекер на двох (Monobank)

Дата узгодження: 2026-07-06. Старт трекінгу даних — константа `TRACKING_START` на сервері.

## 1. Що будуємо

PWA для двох користувачів (пара або партнери), які ведуть **спільний бюджет** на базі
спільного рахунку Monobank (2 картки = 2 людини). Застосунок трекає доходи/витрати,
авто-категоризує, розподіляє дохід за правилом, рахує ліміти, попереджає про
перевитрати, веде цілі-накопичення та трекає інвестиційний портфель. Хоститься на
власному сервері.

## 2. Модель грошей (ядро логіки)

### Конверти (envelopes) — віртуальний облік
Гроші фізично лежать на спільному рахунку; апка веде віртуальний поділ доходу:
- **Інвестиції — 15%** → фізично одразу купуємо ETF (S&P500) через брокера.
- **Розваги — 15%** → фізично відкладаються.
- **Побут — 70%** → щоденні витрати.

### Цикл
- Починається **від приходу більшої частини ЗП** (поріг — `cycleAnchorMin` у налаштуваннях). Менші частини доходу просто додаються до бюджету циклу.
- Тривалість — до наступного приходу більшої частини (місячний цикл).

### Денний ліміт на побут
- Самовирівнювання: `(бюджет_побуту − вже_витрачено) ÷ дні_до_кінця_циклу`.
- Перевитратив сьогодні → завтрашній ліміт автоматично менший.

### Розподіл залишку в кінці циклу
- Невитрачений побут **не переноситься**, а розподіляється **вручну** між:
  - рахунком **«Цілі»** (накопичення на забаганки),
  - **інвестиціями**.
- Пропорцію визначаємо індивідуально кожного разу (апка показує залишок і питає).

### Детекція доходу
- **Правила + підтвердження**: великі вхідні транзакції апка позначає «ймовірно дохід»
  (за сумою/відправником), користувач підтверджує одним тапом → запускається правило 15/15/70.
- Це відсіює повернення, перекази між своїми, поповнення цілей.

## 3. Рахунок «Цілі» (goals)

Окремий Monobank-рахунок/банка під тим самим токеном (трекається авто).
- Кілька **цілей** з: цільовою сумою, **дедлайном** (до коли назбирати), прогрес-баром.
- Розподіл приходу між цілями (напр. зайшло 10к → 7к на одну ціль, 3к на іншу).
- **Переливання** коштів між цілями.
- Коли прогрес-бар заповнений → статус «можна купувати».

## 4. Інвестиції

- Апка нічого не купує — лише трекає.
- Веде **внески** (скільки відкладено/куплено) + **вартість портфеля**: підтягує
  поточну ціну S&P500 ETF (USD) і конвертує в UAH за курсом.
- Показує дохідність.

## 5. Дані та інтеграція

- **Monobank Personal API**: webhook на нові транзакції (реалтайм) + `client-info`
  для виявлення рахунків/банок. Auth: `X-Token`. Rate limit: 1 req/60s на
  client-info та statement; webhook доставку не лімітує.
- **Реєструємо по токену на кожного** (кожен генерує свій зі свого логіну),
  webhook на кожен токен. Транзакцію приписуємо власнику токена, чий webhook її
  доставив; дедуп за `StatementItem.id`. `personId` nullable + перевизначуваний.
- **«Цілі» (jars) тягнемо пулом `client-info`** кожні ~3–5 хв (не через webhook —
  jar-події webhook не гарантує). `client-info.jars[]` віддає `balance` і `goal`.
- **Готівка**: швидка форма «+витрата» (сума, категорія, конверт, хто).
- **Категоризація**: авто за MCC + користувацькі правила («цей мерчант = продукти»),
  з можливістю перевизначити.
- **Особа**: визначається автоматично за токеном картки.
- **Валюта**: UAH базова; ETF трекається в USD→UAH. Курс — НБУ API.
- **Історія**: трекінг ведеться з моменту старту (webhook + пул), але історію
  **можна доімпортувати на вимогу** — `POST /api/mono/sync-history` `{ days }`
  (1–31, дефолт 30) тягне виписку з Mono Statement API у фоні (202 одразу),
  дедуп ідемпотентний за `monoId`. Ліміт 31 день — обмеження Mono API; між
  рахунками чекаємо 62с (rate limit 1 req/60с). _(Рішення змінене 2026-07-11:
  спершу планувалось «без імпорту».)_

## 6. Вечірній розбір (щоденне нагадування)

Апка ввечері просить розкидати вручну те, що автоматика не змогла:
- **категорію**, яку MCC не вгадав;
- **конверт** (побут / розваги).

## 7. Дашборд, фільтри, чарти

- Дашборд: баланси конвертів, денний ліміт, прогрес до кінця циклу, статус лімітів,
  цілі, портфель.
- Фільтри: за типом/категорією, за людиною, за сумою/кількістю витрат.
- Чарти: витрати за категоріями, динаміка в часі, побут vs ліміт, портфель.

## 8. Push-сповіщення

- **Прихід доходу** → «відклади 15% в ETF, 15% у розваги».
- **Перевитрата денного ліміту** → «час економити».
- **Прогноз перевитрати** (превентивно) → «при такому темпі не вистачить».
- **Кінець циклу** → розподіл залишку побуту.
- **Вечірнє нагадування** → розкидати нерозподілені транзакції по кожному з двох.

## 9. Доступ і безпека

- Логін, **2 акаунти**, спільні дані; реєстрація закривається після другого.
- Mono-токени шифруються в БД. HTTPS обов'язково (потрібен для webhook).

## 10. Технічний стек

- **Frontend**: React + Vite + TypeScript, PWA (vite-plugin-pwa, service worker),
  TanStack Query, Recharts (чарти), Tailwind. Web Push (VAPID) для сповіщень.
- **Backend**: Node.js + TypeScript, Fastify. Prisma ORM.
- **БД**: PostgreSQL.
- **Auth**: сесії + argon2 (2 користувачі).
- **Планувальник**: node-cron (денний ліміт, вечірнє нагадування, кінець циклу,
  оновлення цін/курсу).
- **Інтеграції**: Monobank Personal API (webhook + client-info), НБУ API (курс),
  безкоштовне джерело ціни ETF (напр. Stooq/Yahoo).
- **Деплой**: Docker Compose (app + Postgres + Caddy з авто-HTTPS/Let's Encrypt).

## 11. План по фазах

**Фаза 1 — дані + дашборд (MVP):**
Mono webhook + client-info, авто-категоризація (MCC + правила), конверти 15/15/70,
детекція доходу з підтвердженням, денний ліміт, готівка, базовий дашборд + чарти + фільтри,
логін на 2 акаунти, Docker/Caddy деплой.

**Фаза 2 — цілі + сповіщення:**
Рахунок «Цілі» з таргетами/дедлайнами/прогресом, переливання між цілями,
розподіл залишку в кінці циклу, Web Push (усі 5 типів), вечірній розбір.

**Фаза 3 — інвестиції:**
Трекінг внесків + вартість портфеля ETF (USD→UAH), дохідність, чарти портфеля.

## 12. Розвідка Monobank API (виконано)

Підтверджено по кількох SDK/дзеркалах (прямий доступ до api.monobank.ua заблоковано мережею):

- **Auth**: `X-Token: <персональний токен>`.
- **`GET /personal/client-info`** → `accounts[]` + `jars[]`.
  - `jars[]`: `id, sendId, title, description, currencyCode, balance, goal`.
  - `accounts[]`: `id, sendId, balance, creditLimit, type, currencyCode, cashbackType, maskedPan[], iban`.
- **StatementItem**: `id, time`(unix), `description, comment, mcc, originalMcc, hold,
  amount`(копійки, зі знаком), `operationAmount, currencyCode`(ISO4217: 980=UAH,840=USD),
  `commissionRate, cashbackAmount, balance, receiptId, counterName, counterIban, counterEdrpou`.
- **Webhook**: `POST /personal/webhook {webHookUrl}`; payload
  `{"type":"StatementItem","data":{"account":"<id>","statementItem":{…}}}`; валідація GET→200.
- **Rate limit**: 1 req/60s на client-info та statement.

**Рішення за результатами розвідки:**
- Jar-події через webhook не гарантовані → баланси «Цілей» тягнемо пулом `client-info` кожні ~3–5 хв.
- Автор транзакції у спільному рахунку API не віддає → атрибуція по токену + дедуп за `id`
  (див. §5), `personId` nullable/перевизначуваний. Емпірично перевіримо на Фазі 1.
- Потрібен домен + публічний HTTPS для webhook (Caddy зробить сертифікат).
