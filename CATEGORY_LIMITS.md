# Категорії та ліміти для 70% (LIVING) — узгоджений план

> Дизайн покатегорійних лімітів усередині конверта LIVING. Джерела істини по решті логіки: `SPEC.md`, `DATA_MODEL.md`.

## Мета й контекст

FinTrack уже має **дві незалежні осі**: `Category` («що») і `Envelope` («який бюджет»). 70% на життя — це конверт `LIVING`, і бюджет/ліміт зараз існує **лише на рівні конверта** (`computeCycleStats` рахує `livingBudget` і самовирівнювальний денний ліміт). Бракує рівно одного: **ліміту/плану на рівні категорії**.

Мета: дати кожній LIVING-категорії м'який план на цикл (видимість + попередження, денний ліміт лишається головним числом), коректно поводитися з «грудкуватими» рахунками (комуналка прилітає раз на місяць великим шматком), і **не змушувати виставляти ліміти вручну** — після першого прожитого циклу застосунок сам порахує пропозиції з реальних витрат.

## Узгоджені рішення

- **Ліміти м'які** (видимість): прогрес-бари + попередження, покупку не блокують. Герой-число — єдиний денний ліміт.
- **Немає жорсткого fixed/flexible.** Проблема — *грудкуватість*, не фіксованість. Рішення: у категорії є `plannedAmount` (план на цикл) + тумблер `reserveUpfront` (за замовч. off). `reserveUpfront=true` (комуналка) → **оцінка** резервується з пулу наперед, щоб денний ліміт не брехав; сума-оцінка може плавати.
- **Продукти й Кафе — окремі.** Одяг, Дім, Інше — лишаються.
- **Ліміти спільні на пару** (household-level). Людина (`Transaction.userId`) — тільки для аналітики, у бюджет не входить.
- **План переноситься як дефолт**, редагується; на екрані — індикатор «сума планів vs гнучкий бюджет», але не змушуємо сходитись.
- **Заповнення лімітів — детермінована евристика** (без LLM) на закритті циклу з історії витрат. LLM-порада — можливе майбутнє.
- **Розкатка:** Цикл 1 = чистий трекінг (плани `null`, поведінка як зараз). На закритті → пропозиції. Цикл 2+ → ліміти активні.

## Фінальний набір LIVING-категорій

Продукти · Кафе · Транспорт · Комуналка · **Дитина** (rename `Діти`) · **Коти** (нова) · **Косметика** (нова) · **Медицина** (rename `Здоров'я`) · Одяг · Дім · Інше.

Entertainment (Розваги, Підписки) — **без** покатегорійних лімітів у v1.

## Модель даних (мінімальна)

Додати **два поля** на `Category` (`server/prisma/schema.prisma`) — **без нової таблиці**:

```prisma
plannedAmount  BigInt?  // м'який план на цикл у мінор. одиницях; null = ще не задано
reserveUpfront Boolean  @default(false) // резервувати наперед (грудкуваті рахунки)
```

Обґрунтування: «переноситься як дефолт, редагується» = редагування оновлює дефолт; евристика перезаписує на кожному закритті. Per-cycle snapshot (`CycleCategoryBudget`) не потрібен для м'яких лімітів у v1 — додамо пізніше, якщо захочемо історію планів по циклах.

## Математика денного ліміту (`server/src/mono/cycle.ts`, `computeCycleStats`)

Зараз: `dailyLimit = (livingBudget − livingSpent) / daysLeft`. Змінюємо базу на **гнучкий пул** (резерв виноситься наперед; резерв тримає лише *невитрачену* частину оцінки, щоб не рахувати двічі):

```
R = категорії з reserveUpfront=true
reservedCommitment = Σ_{c∈R} max(plannedAmount_c, spent_c)   // перевитрата оцінки збільшує резерв
flexibleSpent      = livingSpent − Σ_{c∈R} spent_c
flexibleBudget     = livingBudget − reservedCommitment
flexibleRemaining  = flexibleBudget − flexibleSpent
dailyLimit         = flexibleRemaining > 0 ? flexibleRemaining / daysLeft : 0
safeToday          = dailyLimit − flexibleSpentToday
```

Перевірка на комуналці (оцінка 3000): до оплати резерв тримає 3000; оплата 2800 **не рухає** гнучкий денний ліміт; факт 3500 → резерв стає 3500, пул просідає на 500 + попередження.

Аггрегувати заодно **spent по кожній категорії** (розширити цикл-loop, який уже читає `cycleId` txs) і повернути `byCategory: [{categoryId, spent, planned, reserveUpfront}]`. Розширити інтерфейс `CycleStats` полями `reservedCommitment`, `flexibleBudget`, `flexibleRemaining`, `byCategory`. Перевикористати наявні `daysBetweenInclusive`/`sameLocalDay` (`server/src/time.ts`).

## Евристика підбору лімітів (новий модуль `server/src/mono/suggestLimits.ts`)

Вхід: закриті цикли (>=1). Для кожної LIVING-категорії:

- `typical` = медіана (при 1 циклі — його сума) витрат по категорії за цикл;
- `suggestedPlan` = `typical` + буфер (~+10–15%, округлити до 100);
- `reserveUpfront` авто-пропозиція = детект грудкуватості (≥~70% витрат категорії в одній транзакції, або ≤2 великі транз/цикл) → комуналка спрацює;
- якщо `Σ suggestedPlan(non-reserved)` > `flexibleBudget` — пропорційно зменшити + позначити категорії-перевитрати.

Вихід: `[{categoryId, name, spentLastCycle, suggestedPlan, reserveUpfront, note}]`.

Ендпоінти (у cycle-роутах): `GET /api/cycles/:id/suggested-budgets` (порахувати), `POST /api/cycles/:id/apply-budgets` (прийняті значення → `Category.plannedAmount`/`reserveUpfront`). Тригер — на закритті циклу (закриття вже в `openCycle`).

## Перевірка

1. **Юніт `computeCycleStats`**: сценарії комуналки (до/після оплати в межах оцінки → денний ліміт не рухається; перевитрата → просідає на різницю). Перевірити `flexibleRemaining`/`safeToday`/`byCategory`.
2. `npm run -w server build` + `npx prisma migrate dev` на dev-БД; переконатись, що rename не осиротив транзакції (`categoryId` збереглись).
3. Засіяти цикл з транзакціями по категоріях + грудкувата комуналка → `GET /api/dashboard`: коректні денний ліміт, рядок резерву, прогрес-бари.
4. `GET /api/cycles/:id/suggested-budgets` на цьому циклі → комуналка позначена `reserveUpfront`, сума пропозицій у межах гнучкого бюджету; `apply-budgets` → значення осіли в `Category`.
5. Прогнати веб-дашборд (dev-сервер) — бачити прогрес-бари, рядок «Зарезервовано», денний ліміт з гнучкого пулу.
